# todo-list-with-a-twist

A learning project about event-driven architecture in Go. The domain is a deliberately simple to-do list, so the interesting part is the architecture around it: a Postgres store, versioned migrations, and Kafka events consumed by a background worker that will generate AI suggestions for each task.

## Architecture

```
Browser ----> server (cmd/todo)
              1. write the task to Postgres      (synchronous)
              2. publish an event to Kafka        (created / edited / deleted)
              3. redirect

worker (cmd/worker) <---- consumes the "tasks" topic, one event at a time
              handle(event)   → currently logs; planned: ask an LLM for suggested steps
              commit offset   → only after handle succeeds
```

### Design decisions

- **CRUD stays synchronous.** Saving a task is fast, so the user waits for the database write and sees the result immediately. The queue is reserved for slow work (LLM calls) that shouldn't block a request. An earlier version routed every write through Kafka; I dropped it because it added latency and failure modes without any benefit for simple CRUD.
- **Single partition.** The `tasks` topic has one partition so events are processed in strict order (a task's "edited" can never overtake its "created"). That caps throughput at one consumer, which is fine at this scale; the next step would be partitioning by task ID, which keeps per-task ordering.
- **At-least-once delivery.** The worker commits an offset only after `handle` succeeds, and retries with a delay until it does. A crash mid-event means the event is redelivered, so handlers must be idempotent.
- **Idempotent writes.** Task IDs are UUIDv7, generated by the server before the write. `Create` uses `INSERT ... ON CONFLICT DO NOTHING`, so replaying a "created" event is harmless. UUIDv7 is time-ordered, which also gives a natural oldest-first ordering.
- **Storage behind an interface.** `task.Store` has an in-memory implementation (used in tests) and a Postgres one (`database/sql` + `lib/pq`). Schema changes go through versioned [Goose](https://github.com/pressly/goose) migrations instead of `CREATE TABLE` at startup.

### Known gap: the dual write

The server writes to Postgres and then publishes to Kafka, as two separate steps. If the publish fails, the task is saved but no event is sent, and the worker never hears about it. Today that failure is only logged. The standard fix is the **transactional outbox**: write the event to an `outbox` table in the same transaction as the task, and have a relay publish from that table. This is on the roadmap.

## Running it

Requirements: Go 1.27+, Docker with Compose.

```sh
make up      # Postgres, Kafka, Adminer, Kafka UI; runs migrations automatically
make topic   # create the "tasks" topic (first run, or after `make reset`)

DATABASE_URL="postgres://todo:todo@localhost:5432/todo?sslmode=disable" make run
go run ./cmd/worker    # in a second terminal
```

| URL                   |   What                                               |
|-----------------------|------------------------------------------------------|
| http://localhost:8080 | the app                                              |
| http://localhost:8081 | Adminer (server `postgres`, user/password/db `todo`) |
| http://localhost:8082 | Kafka UI                                             |

Other useful targets (`make help` lists all of them):

| Target | Does |
|---|---|
| `make test` | run all tests |
| `make kafka` | print every event on the `tasks` topic |
| `make migrate-status` / `migrate-up` / `migrate-down` | manage migrations by hand |
| `make down` | stop containers, keep data |
| `make reset` | stop containers and **delete** all Postgres and Kafka data |

## Project layout

```
cmd/todo        HTTP server
cmd/worker      Kafka consumer
cmd/migrate     Goose migration runner (also run by the `migrate` compose service)
db/migrations   SQL migrations, embedded into the migrate binary
internal/task   domain types: Task, Store interface, event messages
internal/storage  MemoryStore and PostgresStore
internal/queue  Kafka producer and consumer (confluent-kafka-go)
internal/server HTTP handlers
web             embedded templates and static files
```
